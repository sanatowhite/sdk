# 0008 — `:logkit` is a log pipeline, not a detector; `:core-telemetry` still does the detecting

## Context

We needed a logging SDK: multi-threaded, non-blocking for callers, order-consistent under concurrency, compressed-and-encrypted on disk, capped at a 5MB total budget with oldest-first eviction, and able to capture crash/ANR stack traces "as much as possible" so a user can share the log file for troubleshooting.

The obvious first draft makes the logging SDK also *detect* crashes/ANR/jank — install its own `Thread.UncaughtExceptionHandler`, run its own ANR reaper, etc. That draft was rejected mid-design (user-initiated: "崩溃卡顿ANR 是不是应该是发生时，有 APM SDK 来写入 logger SDK，而不是 log 来完成这些任务？") once it became clear this repo already has a detection layer, `:core-telemetry`, with a working `CrashRecorder`, `AnrExitInfoReaper`, `ForegroundExitBeacon`, and `ScreenJankReporter` — and installing a second `UncaughtExceptionHandler` alongside `CrashRecorder` would race the two handlers, double-write the same crash, and make `:logkit`'s public API permanently carry detection-shaped surface it would then have to freeze (additive-only, forever, once published).

## Consequences considered and rejected

- **`:logkit` detects its own crashes/ANRs**: rejected. Two `Thread.setDefaultUncaughtExceptionHandler` installers race (last-installed runs first, chains outward) with no way to guarantee ordering relative to `CrashRecorder`; a `flushBlocking`-style synchronous flush inside a *second* handler could burn the process's remaining post-crash budget before `CrashRecorder`'s own handler (or Crashlytics, further outward) gets to run.
- **`:core-telemetry` depends on `:logkit`**: rejected. It would add a real edge to `verifyModuleGraph`'s `allowedProjectDeps` map, make `:core-telemetry` no longer independently reusable without `:logkit`, and — the sharper problem — `:logkit` is a candidate for the ADR-0001 subtree-mirror publish path, and a mirrored single-module repo has no `:core-telemetry` to depend on either direction.
- **A shared `Logger` interface in `:core-common`**: rejected as unnecessary indirection. `:core-common` has zero Android dependencies and zero opinions about crypto/threading; forcing the log pipeline's shape through it would make `:core-common` a dependency of a module (`:logkit`) that is itself supposed to have zero internal dependencies.

## Decision

- **`:logkit` is purely a pipeline**: level → in-memory MPSC-ish queue (assign the global sequence number on the *caller's* thread, inside a short lock shared with the enqueue, so admission order matches the written order under concurrency) → single writer thread → deflate → AES-256-GCM (ECIES/P-256 hybrid envelope; see `logkit/README.md` for why ECIES was chosen over RSA-OAEP) → rotating files, 1MB/file, 5MB total budget, evict lowest `fileSeq` (never mtime). It contains no `Thread.UncaughtExceptionHandler`, no ANR reaper, no watchdog, no `ContentProvider`. This is codified as rule 5 of "The five `:logkit` rules" in `CLAUDE.md`.
- **Detection stays in `:core-telemetry`, unchanged.** `CrashRecorder`, `AnrExitInfoReaper`, `ForegroundExitBeacon`, `ScreenJankReporter` all keep doing exactly what they did before this feature existed.
- **Two channels carry signals from `:core-telemetry` into `:logkit`, both living in `:app`:**
  1. `LogKitTelemetry : Telemetry`, bound `@IntoSet` — covers every event-shaped signal (`startup`/`frame`/`networkRequest`/`crash`/`anr`/`screenView`/`event`) for free, the same way `RingLogBuffer` already does. **Zero `:core-telemetry` changes.**
  2. `DiagnosticLogSink`, a new `fun interface` owned by `:core-telemetry` (mirrors `:core-net`'s existing `NetworkMetricsSink` pattern: the *producer* module owns the interface, `:app` supplies the bridge, the two `core-*` modules stay mutually unaware of each other). This exists only for the two things `Telemetry` structurally cannot carry: the crash handler itself (`CrashRecorder.install(context, logSink: DiagnosticLogSink = DiagnosticLogSink.NoOp)` — a defaulted constructor parameter, not a mutable static, because the call site is already hand-written in `AppTemplateApp.attachBaseContext`, before Hilt's graph exists) and the ANR trace bytes (`AnrExitInfoReaper.readAnrTrace()`, a new, non-consuming, separately-callable method — `reapNewAnrExits()` itself is destructively consuming and must keep exactly one caller per launch).
- **The one thing that could not move to the detection layer: crash-time persistence.** Detecting a crash and flattening a stack trace is cheap and can happen anywhere; getting the *queued-but-not-yet-written* log records onto disk before the process dies cannot happen anywhere except inside the log pipeline itself, synchronously, on the crashing thread. So `:logkit`'s public API includes `flushBlocking(timeoutMillis)` and `fatal(tag, message, throwable)` (write-then-auto-flush) as first-class, frozen-API entry points, and `LogKit.install()` must be safe to call from `Application.attachBaseContext` (no IO, no crypto, <2ms) so the pipeline exists before the earliest possible crash.
- **No consent gating in this iteration** (explicit user decision, not an oversight): `UserSettings.telemetryEnabled` stays wired to nothing, logs persist unconditionally once installed. Flagged as a hard pre-launch blocker if this SDK is ever used for a consumer-facing production build — see the risk list in the implementation plan.

## Consequences

- `:core-telemetry`'s `verifyModuleGraph` entry stays `setOf(":core-common")`, unchanged — the entire point of routing through `DiagnosticLogSink` instead of a direct dependency.
- `:logkit`'s public API surface stays narrow enough to plausibly freeze forever: level methods, `fatal`/`flushBlocking`, `stats`/`purge`/`export`, and config. Nothing crash/ANR/jank-shaped ever needed to be added to it.
- The trade-off is two bridging files in `:app` (`LogKitTelemetry.kt`, `LogKitDiagnosticSink.kt`) plus one new interface in `:core-telemetry` (`DiagnosticLogSink.kt`) instead of one. Judged worth it: both `:core-telemetry` and `:logkit` remain independently reusable and independently testable, and a future fork can delete `:logkit` entirely (see `TEMPLATE.md`) without touching `:core-telemetry` at all — `DiagnosticLogSink.NoOp` is the default.
